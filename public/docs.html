Abstract Messenger — Documentation

Address-based messaging with client-side encrypted payloads on AbstractChain.

Overview

Abstract Messenger enables address-based chats. Messages are transmitted as on-chain transactions on AbstractChain, and mirrored to an indexed datastore to enable fast retrieval and cross-device availability. Payloads are encrypted client-side with automatic end‑to‑end encryption that requires no user input.

Key Advantages over Web2

  • Anonymity: Chats are address-based; no email/phone/SSO.
  • Ownership: Messages are tied to your wallet; no centralized accounts.
  • Client-side encryption: Payloads are encrypted with AES‑GCM (see Security Notes).
  • Portability: History can be reconstructed from chain, independent of any single server.
  • Transparency: Message metadata is verifiable; payloads remain unreadable to others.

How Encryption Works

Each device generates a local ECDH keypair and derives a shared secret per peer. Messages are encrypted with AES‑GCM using a fresh IV on every send. Public keys are exchanged automatically inside the encrypted payload header to keep the UX frictionless.

  • E2EE: ECDH (P‑256) per device, shared AES‑GCM key per peer.
  • Cipher: AES‑GCM (256‑bit), random IV per message.
  • Prefix v2: enc:v2:<sender_pub>:<iv_base64>:<ciphertext_base64>.
  • Legacy v1 supported for backwards compatibility: enc:v1:<iv>:<ciphertext>[:<sender_pub>].

Realtime and Reliability

  • Realtime: Supabase Postgres changes subscriptions for instant updates.
  • Fallback: Periodic polling ensures delivery when realtime is unavailable.
  • Recovery: A light chain scanner can reconstruct missing messages from on-chain data.

Profiles and Identity

  • Avatars and usernames are pulled from Abstract Portal by wallet address.
  • If no on-chain username is set, a local nickname can be applied.
  • When no nickname exists, the UI falls back to a shortened address.

Presence and Read Status

  • Online status reflects when the other participant has your chat open.
  • Typing indicators appear in real time while the other user is composing.
  • Read receipts show when the latest outgoing message has been seen.

Session Sending

Session sending allows pre-authorized message transmissions without per-message wallet prompts. Implementation typically relies on smart wallet session keys or permissioned delegates. This UI includes a “Create Session” control and persistence, ready to be wired to wallet APIs that support sessions.

Interface

  • Soft-surface cards with reduced borders and deeper shadows.
  • Modernized search and composer inputs with rounded geometry.
  • Larger avatars and clearer chat list hierarchy.
  • Mobile-friendly layout with stacked panels and touch-ready controls.

Recent Updates

  • Automatic E2EE with per-device ECDH keys and AES‑GCM encryption.
  • Zero‑input key handling: no manual keys required from users.
  • Backward compatible decryption for legacy encrypted payloads.
  • Multi-device sync diagnostics: detailed timing logs for realtime, polling, and chain recovery.

Security Notes

  • Messages are protected by E2EE using per-device ECDH and AES‑GCM.
  • Private keys never leave the device; only public keys are shared.
  • If a device is compromised, that device’s stored messages and keys can be exposed.
  • Clearing local storage resets the device key and breaks decryption of prior E2EE messages on that device.
  • Encrypted payloads stored in Supabase should be treated as public ciphertext.
