Abstract Messenger — Documentation

Address-based messaging with client-side encrypted payloads on AbstractChain.

Overview

Abstract Messenger enables address-based chats. Messages are transmitted as on-chain transactions on AbstractChain, and mirrored to an indexed datastore to enable fast retrieval and cross-device availability. Payloads are encrypted client-side with automatic E2EE using device keys; a legacy fallback may be used until both sides exchange keys.

Key Advantages over Web2

  • Anonymity: Chats are address-based; no email/phone/SSO.
  • Ownership: Messages are tied to your wallet; no centralized accounts.
  • Client-side encryption: Payloads are encrypted with AES‑GCM (see Security Notes).
  • Portability: History can be reconstructed from chain, independent of any single server.
  • Transparency: Message metadata is verifiable; payloads remain unreadable to others.

How Encryption Works

Each device generates a local ECDH keypair. When two devices exchange public keys, a shared secret is derived and used to encrypt payloads with AES‑GCM. The sender’s public key is included in the payload so recipients can derive the same shared key automatically.

  • E2EE derivation: ECDH (device keypairs) → shared secret.
  • Cipher: AES‑GCM (256‑bit), random IV per message.
  • Prefix (E2EE): enc:v2:<sender_pub>:<iv_base64>:<ciphertext_base64>.
  • Legacy fallback: deterministic PBKDF2 key + conversation salt, encoded as enc:v1:<iv_base64>:<ciphertext_base64>[:sender_pub] until keys are exchanged.

Realtime and Reliability

  • Realtime: Supabase Postgres changes subscriptions for instant updates.
  • Fallback: Periodic polling ensures delivery when realtime is unavailable.
  • Recovery: A light chain scanner can reconstruct missing messages from on-chain data.

Profiles and Identity

  • Users set their own display name and avatar directly in the app.
  • Profile updates are stored and synced across devices via the indexed datastore.
  • When no profile is set, the UI falls back to a shortened address.

Presence and Read Status

  • Online status reflects when the other participant has your chat open.
  • Typing indicators appear in real time while the other user is composing.
  • Read receipts show when the latest outgoing message has been seen.

Session Sending

Session sending allows pre-authorized message transmissions without per-message wallet prompts. Implementation typically relies on smart wallet session keys or permissioned delegates. This UI includes a “Create Session” control and persistence, ready to be wired to wallet APIs that support sessions.

Security Notes

  • E2EE keys are stored locally per device; clearing storage can make old E2EE messages unreadable.
  • A compromised device can expose locally cached messages and encryption keys.
  • Legacy v1 derivation is deterministic and not secret; it may appear before E2EE keys are exchanged.
  • Addresses and timestamps are public on-chain; metadata is always visible.
  • Supabase policies allow public read/write of encrypted payloads; treat it as public data.
  • Consider using fresh addresses for stronger unlinkability.
